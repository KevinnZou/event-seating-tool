# 刷新加载问题与安全恢复（2026-10-20）

## 检查与复现

- 4176预览HTTP响应正常。检查的两个内置浏览器同源标签页仍由旧离线缓存加载V0.1，普通刷新继续返回旧版；当时未捕获控制台异常，也未稳定复现用户描述的所有“卡住”形态。
- 独立浏览器测试可复现一个确定缺陷：旧页面持有IndexedDB3连接且不释放时，新版升级4的open持续等待，旧StorageGate只有loading/ready/error三态，因此会无解释地停在检查存储。
- 另一个恢复缺陷：存储门禁或懒加载阻塞时，原更新入口位于其后，用户可能无法访问更新；重复普通刷新仍可能读取旧应用壳。

## 修复

- 监听blocked事件，说明旧标签占用并要求先保存未提交内容再关闭。等待操作仍保持，释放后自动完成升级与显示已有活动，不超时删除或重建数据库。
- versionchange时关闭本页连接并停止读写；低版本打开高版本库的VersionError显示更新说明，不再误报只有存储权限/空间问题。
- 存储加载阶段也提供离线更新状态；应用/存储加载超过10秒后显示排查与修复入口。懒加载失败的错误页同样能进入恢复页。
- `recover.html`是独立静态页面，不依赖React或应用JS块，不读取、清空或重建IndexedDB。联网获取最新Service Worker并激活后返回应用，不注销全部缓存或清空站点数据。它故意不纳入应用离线壳，以便绕过旧应用导航缓存。

## 2026-10-21：Chrome现场白屏的补充定位

用户补充截图后改为检查实际Chrome，而非仅检查内置浏览器：首页测试不能代表Chrome活动深链接。通过原生窗口发现“重新加载此网站？系统可能不会保存您所做的更改”确认框；取消阻塞后控制台明确报出旧版本`assets/App-CroZAI5W.js`的404与`Failed to fetch dynamically imported module`。此前仅通过空白页截图无法区分这两种问题。

本轮修复：

- 已提交IndexedDB的活动不再因未下载外部JSON而注册beforeunload；备份提醒仍保留。新增测试先在旧代码上双引擎失败，确认触发beforeunload，再验证修复后连续刷新无原生弹窗。
- `npm run preview`改为将dist复制到独立临时目录后提供固定版本快照；后续build清理dist不再删除正在预览的脚本。需要更新预览时重启该命令，再通过应用更新入口切换。默认地址仍4176；strictPort阻止误用其他端口。
- 生产更新测试改为操作`tmp/pages-preview`副本，修改测试Service Worker不再触及用户预览的dist。临时文件不进入Git、lint或格式检查。
- index.html内置不依赖React的启动提示与原生修复链接，即使入口JS失败也有可操作说明；React模块错误不再直接误称“无法加载本地数据”。恢复入口保留原活动Hash及场地图视图，不删除缓存或IndexedDB。

不要用清理站点数据、删除IndexedDB、换端口重建活动来修复这一问题。此前“两个内置主页可刷新”的结论只适用于那些页面，不足以覆盖此次Chrome活动页。
